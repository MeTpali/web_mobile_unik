# План разработки лабораторной работы № 1

Тема: «Взаимодействие с web-клиентом».  
Вариант № 6: генератор случайных чисел.  
Статус: выполнены этапы 1–5. Адаптивная вёрстка и доступность проверены в Chrome; ограничения проверок описаны в README. Версия браузера Авроры пока неизвестна.

## 1. Цель и ожидаемый результат

Разработать клиент-серверное приложение, в котором пользователь вводит две границы диапазона в браузере, нажимает кнопку и получает случайное целое число, сгенерированное сервером.

Приложение должно запускаться на ПК и быть доступным в локальной сети. На защите необходимо продемонстрировать его работу в браузере ПК и в браузере телефона под управлением ОС Аврора.

Весь проект первой лабораторной размещается в папке `lab-01`. Добавлена основа клиента и сервера; установка и запуск описаны в README.md.

## 3. Принятые решения и границы работы

### 3.1. Функциональные правила

Условие не уточняет тип чисел и включение границ. Для реализации принимаются следующие правила; это решения проекта, а не дополнительные требования преподавателя:

- Генерируются целые числа.
- Нижняя и верхняя границы включаются в диапазон.
- Отрицательные числа и ноль разрешены.
- При одинаковых границах результат равен указанному числу.
- Если минимум больше максимума, выводится ошибка; значения автоматически не переставляются.
- Каждое нажатие запускает отдельную генерацию. Повторение предыдущего результата допустимо.
- Начальные значения формы: минимум 1, максимум 100.
- Поддерживаемые границы: от −1 000 000 000 до 1 000 000 000 включительно. Это явно указанный предел приложения, позволяющий избежать проблем с точностью и ограничениями генератора.
- Дробные, пустые и нечисловые значения отклоняются.
- Интерфейс и пользовательские сообщения оформляются на русском языке.

### 3.2. Что входит в результат

- React-интерфейс с формой и результатом.
- Серверный HTTP API генерации.
- Проверка данных на клиенте и сервере.
- Состояния ожидания, успеха и ошибки.
- Адаптивная вёрстка.
- Сборка и запуск на ПК для доступа из локальной сети.
- Проверки серверной логики и ручные сценарии проверки интерфейса.
- README с инструкциями запуска, проверки и демонстрации.

### 3.3. Что не требуется для первой лабораторной

База данных, учётные записи, авторизация, облачный хостинг, история генераций, графики, WebSocket и нативное мобильное приложение не входят в исходный объём работы. WebSocket и мобильный клиент относятся ко второй лабораторной. Серверную функцию генерации следует отделить от HTTP-обработчика, чтобы впоследствии её можно было использовать повторно.

## 5. Архитектура и поток данных

Последовательность одного пользовательского действия:

1. Пользователь изменяет поля формы.
2. Клиент проверяет заполнение, целочисленность, допустимые границы и их порядок.
3. При ошибке запрос не отправляется, рядом с формой появляется объяснение.
4. При корректных данных клиент устанавливает состояние ожидания и отправляет `POST /api/random`.
5. Сервер заново проверяет тело запроса независимо от клиента.
6. Серверная функция генерирует число и возвращает его обработчику.
7. Обработчик отправляет JSON-ответ.
8. Клиент проверяет HTTP-статус, читает ответ и отображает результат либо ошибку.
9. Состояние ожидания завершается, повторная отправка становится доступной.

Генерация выполняется только на сервере. React хранит значения полей и состояние интерфейса, но не вычисляет случайный результат.

### 5.1. Режим разработки

- Express обслуживает API на порту 3000.
- Vite обслуживает клиент на порту 5173.
- Vite перенаправляет запросы `/api` на Express через proxy.
- Клиент всегда использует относительный адрес `/api/random`.
- В браузерный код не зашивается адрес `localhost:3000`, который на телефоне означал бы сам телефон.

### 5.2. Режим демонстрации

- Vite собирает интерфейс в папку `dist`.
- Express раздаёт `dist` и обслуживает `/api/random` на одном порту.
- Сервер принимает подключения на `0.0.0.0`.
- На ПК приложение открывается по `http://localhost:3000`.
- На телефоне приложение открывается по `http://<локальный-IP-ПК>:3000`.
- Библиотеки и стили входят в локальную сборку; интернет и внешние CDN для демонстрации не требуются.

Один адрес для интерфейса и API упрощает запуск и исключает необходимость отдельной настройки CORS в режиме демонстрации.

## 7. Контракт API

### 7.1. Запрос генерации

- Метод: `POST`.
- Путь: `/api/random`.
- Тип содержимого: `application/json`.
- Обязательные поля: `min` и `max`.
- Оба поля должны быть JSON-числами, представляющими целые значения в поддерживаемых пределах.
- Пример данных: `{"min":1,"max":100}`.

API не должен молча преобразовывать строки, `null`, логические значения или массивы в числа. Корневое значение тела должно быть объектом.

### 7.2. Успешный ответ

- HTTP-статус: `200`.
- Поля: `min`, `max`, `value`.
- Пример: `{"min":1,"max":100,"value":42}`.
- Инвариант: `value` — целое число, для которого `min ≤ value ≤ max`.

Возвращённые границы позволяют однозначно подписать результат диапазоном, для которого он был получен.

### 7.3. Ошибки

| Ситуация                                          | Статус | Ожидаемое поведение                                    |
| ------------------------------------------------- | ------ | ------------------------------------------------------ |
| Отсутствуют поля, неверны типы или порядок границ | 400    | JSON с понятным описанием ошибки                       |
| Некорректный JSON                                 | 400    | Единый JSON-формат ошибки                              |
| Неподдерживаемый тип содержимого                  | 415    | Сообщение об ожидании JSON                             |
| Слишком большое тело запроса                      | 413    | Отказ в обработке                                      |
| Неизвестный API-маршрут                           | 404    | JSON с сообщением о неизвестном маршруте               |
| Непредвиденная серверная ошибка                   | 500    | Общее сообщение клиенту, подробности в консоли сервера |

Общий формат ошибки: `{"error":{"code":"INVALID_RANGE","message":"Минимум не должен превышать максимум"}}`. Для разных причин использовать подходящие стабильные коды. Ограничить размер JSON-тела небольшим значением, например 1 КБ: для двух чисел этого достаточно.

### 7.4. Алгоритм генерации

- Проверить валидность диапазона до обращения к генератору.
- Если границы совпадают, вернуть эту границу.
- В остальных случаях использовать `crypto.randomInt(min, max + 1)`, поскольку верхняя граница этой функции исключается.
- Принятый предел ±1 000 000 000 оставляет диапазон в пределах возможностей выбранного генератора и точного представления чисел.
- Не использовать округление случайного вещественного числа через `Math.round`, создающее неодинаковые вероятности крайних значений.
- Не запрещать повторы: они являются нормальным свойством случайной генерации.

## 8. Интерфейс и поведение формы

### 8.1. Состав страницы

- Заголовок «Генератор случайных чисел».

- Подсказка о допустимых значениях.
- Кнопка «Сгенерировать».
- Область результата с крупным числом и исходным диапазоном.
- Область сообщения об ошибке.
- Небольшая подпись с номером лабораторной и вариантом, если она не мешает основному интерфейсу.

### 8.2. Состояния

| Состояние                         | Отображение и действия                                                      |
| --------------------------------- | --------------------------------------------------------------------------- |
| До первого запроса                | Подсказка в области результата                                              |
| Некорректный ввод                 | Объяснение ошибки, запрос не отправляется                                   |
| Запрос выполняется                | Текст «Генерация…», отправка и редактирование границ временно заблокированы |
| Успех                             | Число и диапазон, для которого оно получено                                 |
| Ошибка API                        | Сообщение сервера, возможность исправить ввод и повторить                   |
| Нет связи или истёк срок ожидания | Сообщение о недоступности сервера, возможность повторить                    |

При редактировании диапазона предыдущий результат сбрасывается, чтобы не восприниматься как результат для новых границ. При отправке очищается старая ошибка. Состояние ожидания снимается и при успехе, и при неудаче.

На клиенте предусмотреть ограниченное ожидание ответа, например 10 секунд. Способ отмены запроса выбрать с учётом целевого браузера. Не создавать искусственных задержек для показа загрузки.

### 8.3. Проверка ввода

- Хранить текст полей так, чтобы пользователь мог очистить значение или начать ввод отрицательного числа.
- Проверять пустое значение до преобразования: пустая строка не должна превращаться в допустимый ноль.
- Проверять конечность, целочисленность и поддерживаемые пределы.
- Использовать HTML-ограничения формы как помощь пользователю, дополняя их проверкой JavaScript.
- Окончательное решение о допустимости запроса принимает сервер.

### 8.4. Доступность

- Использовать семантическую форму и настоящую кнопку отправки.
- Обеспечить отправку клавишей Enter и навигацию клавишей Tab.
- Сохранить видимый индикатор фокуса.
- Не сообщать об ошибке только цветом.
- Настроить объявление результата и ошибок средствами `aria-live` или подходящими ролями.
- Сделать элементы достаточно крупными для касания, ориентировочно не менее 44 px по высоте.
- Проверить читаемость текста и контраст.

## 11. Матрица проверок

### 11.1. Автоматические проверки сервера

| Вход или ситуация                                 | Ожидаемый результат                  |
| ------------------------------------------------- | ------------------------------------ |
| Диапазон 1–100                                    | Целое число от 1 до 100 включительно |
| Диапазон −10…−1                                   | Целое отрицательное число в границах |
| Диапазон −10…10                                   | Целое число в границах               |
| Диапазон 0–0                                      | Всегда 0                             |
| Диапазон 7–7                                      | Всегда 7                             |
| Одинаковые нижние или верхние предельные значения | Соответствующее предельное число     |
| Полный разрешённый диапазон                       | Корректный целочисленный результат   |
| Минимум больше максимума                          | HTTP 400                             |
| Дробная граница                                   | HTTP 400                             |
| Граница вне установленного предела                | HTTP 400                             |
| Нет одного или обоих полей                        | HTTP 400                             |
| Строки, `null`, логические значения вместо чисел  | HTTP 400                             |
| Массив или `null` вместо объекта                  | HTTP 400                             |
| Повреждённый JSON                                 | HTTP 400 и JSON-ошибка               |
| Неверный тип содержимого                          | HTTP 415                             |
| Тело превышает ограничение                        | HTTP 413                             |
| Неизвестный API-адрес                             | HTTP 404 и JSON-ошибка               |

Повторные генерации проверяют целочисленность и попадание в диапазон. Не писать нестабильные тесты, требующие обязательного появления каждой границы или отличия соседних результатов. Такие ожидания не гарантируются случайной генерацией.

### 11.2. Ручные проверки клиента

- Отправка формы не перезагружает страницу.
- Пустые поля не интерпретируются как ноль.
- Ошибочный диапазон объясняется понятным текстом.
- В состоянии ожидания повторная отправка недоступна.
- После успеха и ошибки форма снова доступна.
- Изменение диапазона сбрасывает старый результат.
- Остановка сервера приводит к понятной ошибке связи.
- В консоли браузера нет необработанных ошибок.
- В Network видны отправленные границы и серверный результат.
- Запросы с телефона идут к серверу ПК, а не к `localhost` телефона.
- Вёрстка не создаёт горизонтальный скролл на проверяемых ширинах.
- Кнопка, поля и ошибки доступны при работе с клавиатуры.

## 13. Возможные сложности и способы проверки

| Симптом                                        | Что проверить                                                                                                     |
| ---------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| Телефон не открывает страницу                  | Общая сеть, актуальный IP, порт, `0.0.0.0`, брандмауэр и отсутствие изоляции клиентов Wi-Fi                       |
| Страница открылась, API недоступен             | Относительный адрес `/api/random`, маршрут Express, proxy в режиме разработки                                     |
| Порт занят                                     | Завершить ненужный собственный процесс либо выбрать другой порт и обновить адрес демонстрации                     |

| Аврора не поддерживает часть возможностей      | Установить версию браузера, подобрать цель сборки и при необходимости полифиллы; проверить на устройстве повторно |

Изменения системных сетевых настроек не выполняются на этапе написания проекта без фактической необходимости. Проблемы совместимости решаются по результатам проверки конкретного браузера.
