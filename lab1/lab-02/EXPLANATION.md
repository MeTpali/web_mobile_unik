# Разбор второй лабораторной работы — вариант 6

Этот документ объясняет текущую реализацию. Учебные комментарии находятся также непосредственно в Python, Dart и платформенных файлах. Листинги в отчёте показывают те же исходники без комментариев.

## 1. Что происходит после нажатия кнопки

1. `RangeCard` передаёт нажатие экрану через `onGenerate`.
2. `GeneratorPage._generate` вызывает `FormState.validate`: валидаторы показывают ошибки рядом с полями. Если всё правильно, текст преобразуется в целые числа.
3. `GeneratorController.generate` проверяет состояние подключения и диапазон, сохраняет диапазон запроса, создаёт `request_id` и запускает таймер ожидания.
4. `WebSocketRandomService.generate` превращает объект в JSON-строку и отправляет текстовый кадр в существующий сокет.
5. `random_socket` в FastAPI получает кадр и передаёт текст функции `handle_message`.
6. `handle_message` проверяет структуру и вызывает Python-функцию `generate`. Она вычисляет число и возвращает словарь.
7. FastAPI отправляет словарь как JSON тому же клиенту. Сервис Dart разбирает его в `RandomResponse`.
8. Контроллер сопоставляет ID и диапазон, добавляет результат в историю, отменяет таймер и вызывает `notifyListeners`.
9. `ListenableBuilder` повторно строит UI с новым результатом. Перестроение виджетов не открывает новое соединение.

Случайное число вычисляется на ПК. Телефон проверяет ввод и отображает ответ, но не подменяет серверную генерацию своей.

## 2. Почему код разделён на слои

| Слой | Файлы | Ответственность |
| --- | --- | --- |
| Создание приложения | `main.dart`, `app.dart` | Запуск, тема, создание зависимостей |
| UI | `ui/generator_page.dart`, `ui/generator_cards.dart` | Поля, кнопки, оформление и отображение состояния |
| Контроллер | `controllers/generator_controller.dart` | Действия, состояние, ожидание ответа, история |
| Модели | `models/number_range.dart`, `models/random_result.dart` | Значения диапазона и результата, правила проверки |
| Сервис | `services/random_service.dart` | WebSocket и JSON-протокол |
| Сервер | `backend/app/` | Проверка запросов и генерация числа |

`app.dart` знает конкретный класс `WebSocketRandomService`. Контроллер принимает интерфейс `RandomService`, поэтому для его теста можно передать подставной сервис. UI получает фабрику контроллера и не импортирует WebSocket-сервис. Сервис вообще не зависит от Flutter: только от библиотек Dart и моделей.

Это передача зависимостей через конструктор. Отдельный контейнер или пакет управления состоянием для этого небольшого приложения не требуется.

## 3. Модели и проверка диапазона

`NumberRange` хранит `minimum` и `maximum`. Поля `final` нельзя переназначить. `const` позволяет создавать постоянный объект, если все аргументы известны при компиляции.

`isValid` — геттер, который проверяет обе границы и их порядок. `validateBound` и `validateMaximum` подходят для `TextFormField`: возвращают строку ошибки или `null`, означающий отсутствие ошибки. `int.tryParse` возвращает `null` вместо исключения для неверного ввода.

Проверка есть на трёх уровнях: форма помогает человеку; контроллер защищает вызовы в обход формы; Python проверяет вход независимо от того, какой клиент прислал запрос. Клиентская валидация не заменяет серверную.

`RandomResult` связывает число с диапазоном ответа. Поля текущей формы могут уже измениться, поэтому подпись результата берётся из модели, а не из текстовых контроллеров.

## 4. Жизненный цикл экрана

`GeneratorPage` — `StatefulWidget`: ему нужны сохраняемые поля ввода и методы жизненного цикла. `initState` выполняется один раз и создаёт контроллер через переданную фабрику. `build` может выполняться много раз: при изменении состояния, размера экрана или темы.

`TextEditingController` хранит текст и курсор поля. Его нельзя заново создавать при каждом `build`, иначе ввод будет сбрасываться. `GlobalKey<FormState>` даёт доступ к состоянию формы. Ключ существует столько же, сколько экран.

`String.fromEnvironment('WS_URL')` получает значение из `--dart-define` при сборке. Он не читает переменные окружения телефона. Пользователь может исправить начальный адрес в интерфейсе.

`dispose` освобождает поля и контроллер. Контроллер, в свою очередь, отменяет таймер, подписку и освобождает сервис. Иначе старые обработчики продолжали бы работать после уничтожения экрана.

`SafeArea` учитывает системные панели. `SingleChildScrollView` обеспечивает прокрутку на маленьком экране. `ConstrainedBox` ограничивает ширину на большом. Карточки являются `StatelessWidget`: они получают данные и функции через параметры.

## 5. Состояние контроллера

`GeneratorConnectionState` содержит три возможных статуса: disconnected, connecting, connected. Перечисление безопаснее произвольных строк.

`waiting` вычисляется по наличию `_requestId`. `canGenerate` требует установленного соединения и отсутствия активного запроса. Кнопка блокируется в UI, но контроллер также проверяет это условие: второй запрос нельзя отправить даже прямым вызовом метода.

Поля состояния закрыты символом `_`: в Dart это приватность на уровне библиотеки. Геттеры предоставляют доступ для чтения. `List.unmodifiable` не позволяет внешнему коду изменить историю. Контроллер добавляет новые результаты в начало и хранит максимум десять.

`notifyListeners` сообщает подписчикам об изменении. Это не сетевой вызов. `ListenableBuilder` является подписчиком и обновляет дерево виджетов.

## 6. Зачем request_id, generation и два тайм-аута

`request_id` связывает запрос и ответ. ID другого запроса игнорируется. Ответ должен также содержать тот же диапазон, который был сохранён перед отправкой. Повтор одинакового ID на сервере не возвращает сохранённый результат: каждый запрос запускает новую генерацию.

`_generation` решает другую задачу: различает попытки подключения. Подключение асинхронно. Пользователь может нажать «Отменить», а старый Future завершится позже. После `disconnect` номер поколения меняется; старый обработчик обнаруживает несовпадение и не обновляет состояние нового подключения. У сервиса и контроллера свои счётчики, каждый защищает собственные операции.

Тайм-аут соединения находится в сервисе. Тайм-аут ответа — в контроллере. Оба по умолчанию равны десяти секундам, но относятся к разным операциям. `Future.timeout` прекращает ожидание, не отменяя исходную операцию: поздно открывшийся сокет сервис закрывает отдельно.

Автоматической повторной генерации нет. Это исключает незаметную замену результата после сетевого сбоя. Переподключение выполняется кнопкой.

## 7. WebSocket-сервис

`WebSocket.connect` выполняет handshake. После него сокет является двусторонним потоком: можно отправить несколько запросов через одно соединение. Это отличается от отдельных HTTP-запросов.

`socket.add(jsonEncode(...))` отправляет строку, а значит текстовый кадр. Сервер ожидает именно такой кадр. Целочисленные значения остаются числами JSON; строки и значения вроде `1.0` Python отвергает.

`socket.listen` регистрирует обработчики: данные, ошибку потока и его завершение. `pingInterval` включает транспортный ping/pong для проверки живого соединения. Python-протокол не содержит отдельной прикладной команды ping.

`_decode` последовательно проверяет тип кадра, JSON-объект, ID, тип ответа и поля результата. Даже успешный ответ нужно проверять: неверный сервер или повреждённый протокол не должны порождать некорректную модель.

`StreamController.broadcast` передаёт типизированные события подписчикам. `RandomResponse` — прикладной ответ, `RandomConnectionLost` — потеря транспорта. Ошибка `error` от Python не закрывает сокет; неверный формат и потеря связи приводят к отключению.

`unawaited` явно отмечает Future, завершения которого синхронный метод не ожидает. Это не создание отдельного потока ОС. Безопасность поздних callbacks обеспечивают флаг уничтожения и номер поколения.

## 8. Python-сервер

`run.py` запускает Uvicorn. Конструкция `if __name__ == '__main__'` предотвращает запуск при импорте файла. `app.main:app` указывает модуль и ASGI-приложение.

`app/main.py` определяет FastAPI-маршруты. `/health` использует HTTP для диагностики; генерация во второй лабораторной идёт через `/ws/random`. `await websocket.accept()` завершает подключение. Цикл `receive` различает текст, бинарные кадры и отключение. Ожидание через `await` позволяет серверу обслуживать другие соединения.

`app/protocol.py` отвечает за форму сообщения. Предел 4096 измеряется в байтах UTF-8. `json.loads(..., parse_constant=...)` отвергает NaN и Infinity. Разность множеств ключей находит неизвестные поля. `**result` распаковывает словарь min/max/value в ответ.

`app/generator.py` не знает о FastAPI. `type(value) is int` исключает bool, который в Python наследуется от int. `randbelow(maximum - minimum + 1)` возвращает смещение от нуля; добавление minimum переносит его в нужный диапазон. При одинаковых границах число всегда равно этой границе.

Ошибки диапазона превращаются в обычный JSON-ответ и сохраняют соединение. Непредвиденная ошибка пишется в журнал сервера и закрывает сокет с кодом 1011.

## 9. Платформенная часть Авроры

`aurora/main.cpp` — нативный запуск FlutterApp. CMake собирает исполняемый файл и устанавливает ресурсы. RPM spec описывает пакет; `defines.inc` и `requires.inc` генерируются Flutter, их не надо писать вручную.

В desktop-файле `Name` — имя для пользователя. `OrganizationName.ApplicationName` — технический ID, который обязан совпадать с RPM-пакетом и командой Exec. В нашем случае это `com.example.calculator`. Кириллический заголовок нельзя подставлять вместо `ApplicationName`.

Разрешение `Internet` позволяет сетевой обмен в песочнице Авроры. Без него сама доступность сети на телефоне не означает доступность сети приложению.

Строки о пересоздании платформенных файлов в шаблоне Flutter имеют служебное значение: инструмент может обновлять такие файлы при сборке. Перед ручной платформенной доработкой нужно учитывать это поведение.

## 10. Как проверить и объяснить работу

Запуск и настройка окружения описаны в README клиента и сервера. Физический телефон обращается к IP компьютера, а не к localhost. Для приложения используется ws://IP:8000/ws/random, для проверки в браузере — http://IP:8000/health.

Тесты контроллера используют подставной сервис и проверяют блокировку запросов, ID, историю, диапазон ответа и тайм-аут. Другой тест использует настоящий локальный WebSocket. Виджет-тест проверяет начальный экран на узком устройстве. Серверные тесты проверяют логику, протокол и FastAPI WebSocket. Эти проверки решают разные задачи и не заменяют запуск на реальном телефоне.

На защите удобно сначала показать генерацию на телефоне, затем пройти цепочку UI → контроллер → сервис → Python → ответ. После этого показать одинаковые отрицательные границы, ошибочный ввод и поведение при остановке сервера.

## 11. Короткие ответы на вопросы

- Почему генерация не в Flutter? Основная логика варианта должна выполняться сервером; Flutter — мобильный клиент.
- Почему не HTTP POST? Вторая лабораторная требует сокеты; используется постоянное WebSocket-соединение.
- Почему bool не число для API? Контракт требует целое число, а Python считает bool подклассом int, поэтому проверка сделана строго.
- Почему повторяются случайные значения? Повтор допустим; генератор не обязан выдавать уникальную последовательность.
- Почему история не восстановилась после перезапуска? Она хранится в памяти контроллера, постоянного хранилища нет.
- Почему ошибки проверяются в нескольких местах? UI помогает пользователю, контроллер защищает действия, сервер защищает контракт от любого клиента.
- Почему не создаётся сокет при каждом build? build многократный, а сетевым соединением владеет сервис, связанный с жизненным циклом контроллера.
- Почему doctor не заменяет сборку? Он проверяет окружение, но не гарантирует совместимость файлов проекта и запуск пакета на телефоне.
