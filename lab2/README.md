# Лабораторная №2 · вариант 6 · Расходы

Пошаговый полный показ: [DEMONSTRATION.md](DEMONSTRATION.md).

Задание: `Задания_по_курсу_Разработка_мобильных_и_web_2026.md` в корне курса. Предыдущая работа находится в `lab1/`; новая лабораторная от неё не зависит.

FastAPI предоставляет REST API v1 по HTTPS. Нативный клиент написан на **Qt 5.6 / QML Silica / C++11** для Авроры 5.2.1.200, `armv7hl`. SQLite используется и на сервере, и на телефоне. UI, контроллер, HTTP-транспорт и локальное хранилище разделены.

## Что реализовано

- Расходы: дата, категория, сумма в копейках, комментарий; полный CRUD.
- JWT, восемь часов действия, сохранение сессии через QSettings. Учётные записи `demo` (изменение) и `viewer` (только чтение), начальный пароль у обеих — `demo12345`.
- Проверка данных и ответы 200/201/204/400/401/403/404/500; дополнительно 304/409/415.
- HTTPS с собственным сертификатом, проверкой доверия и имени сервера в клиенте.
- ETag, Cache-Control, Last-Modified, условные GET. Документация OpenAPI `/docs` и `/openapi.json`.
- Тестовая HTML-страница `/` без внешних JS/CSS/CDN, адаптированная для мобильного браузера. Она позволяет выполнить вход и полный CRUD независимо от совместимости Swagger UI.
- SQLite-кэш, offline CRUD и устойчивая очередь операций. Синхронизация вручную и раз в 30 секунд при активном приложении.
- Повторы операций с сохранённым Idempotency-Key; конфликты версий с выбором локальных или серверных данных; tombstones для удалений.
- Обработка таймаута 10 секунд, ошибок TLS/сети, 4xx/5xx и истечения сессии.

## 1. Подготовить сервер один раз

Из корня репозитория:

```bash
cd ~/Unik/web_mobile_unik/lab2/backend
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
```

Узнать IP ПК в общей с телефоном сети:

```bash
ip -4 addr
```

На 26 октября 2026 года Wi-Fi-адрес ПК — **10.215.223.25**, адрес ПК по USB — **192.168.2.8**, SSH телефона — **192.168.2.16**. Адрес SSH телефона не является адресом API. Проверенный обмен с API идёт через Wi-Fi.

Создать сертификат, указав адреса ПК, по которым будет открываться сервер:

```bash
cd ~/Unik/web_mobile_unik/lab2
bash certificates/generate.sh 192.168.0.118 192.168.0.104 10.215.223.25 192.168.2.8
```

Если сертификат уже существует, повторять команду не нужно. Закрытый ключ `server.key` остаётся на ПК. Публичный `server.crt` упаковывается в клиент. Оба файла исключены из Git. При смене IP на адрес, отсутствующий в SAN, нужно выпустить новый сертификат, пересобрать клиент и заново подтвердить доверие в браузере. Скрипт не перезаписывает существующую ключевую пару: сначала перенесите её в резервный каталог.

## 2. Запустить сервер

```bash
cd ~/Unik/web_mobile_unik/lab2/backend
.venv/bin/python run.py
```

Оставить терминал открытым. Остановка — Ctrl+C. Сервер слушает все IPv4-интерфейсы на порту **8443**, схема **https**. База и JWT-ключ сохраняются в `backend/data/` и не входят в Git.

Проверка из второго терминала на ПК:

```bash
cd ~/Unik/web_mobile_unik/lab2
curl --cacert certificates/server.crt https://10.215.223.25:8443/health
```

Ожидается `{"status":"ok"}`. Не используйте `curl -k` для проверки корректности TLS: он отключает проверку сертификата.

## 3. Открыть браузерную часть

На ПК и на телефоне открыть **https://10.215.223.25:8443/**. Для Swagger — **https://10.215.223.25:8443/docs**.

Сертификат учебный и самоподписанный. Браузер должен доверять `server.crt` либо разрешать исключение для этого конкретного сертификата. Сверить отпечаток можно на ПК:

```bash
openssl x509 -in certificates/server.crt -noout -fingerprint -sha256
```

Далее войти как `demo` / `demo12345`, создать расход, обновить список, изменить запись и удалить её. Для `viewer` / `demo12345` создание вернёт 403; список этого аккаунта отдельный.

Страница показывает HTTP-код, заголовки и тело последнего ответа. При сетевой ошибке браузерной мутации сначала обновите список: этот вспомогательный интерфейс не имеет собственной offline-очереди. Основной offline-клиент — нативное приложение.

## 4. Собрать и подписать клиент

Для текущего установленного PSDK:

```bash
cd ~/Unik/web_mobile_unik/lab2
bash tools/build-client.sh
```

Скрипт использует `~/AuroraPlatformSDK/sdks/aurora_psdk`, target `AuroraOS-5.2.1.200-base-armv7hl`, штатную общедоступную ключевую пару разработчика из `~/AuroraOS/package-signing`. Другие пути можно передать переменными `LAB_PSDK`, `LAB_SDK`, `LAB_TARGET`. Для этой сборки target должен уже содержать зависимости из RPM spec.

Сборка сохраняет журнал `client/build.log`, готовый подписанный пакет — `client/RPMS/com.example.expenseslab2-1.0.0-4.armv7hl.rpm`. В нём есть приложение и отдельный исполняемый файл тестов. Публичный сертификат HTTPS также включён в пакет; серверный закрытый ключ туда не попадает.

## 5. Установить и открыть на телефоне

```bash
cd ~/Unik/web_mobile_unik/lab2
scp -O client/RPMS/com.example.expenseslab2-1.0.0-4.armv7hl.rpm defaultuser@192.168.2.16:/home/defaultuser/
ssh defaultuser@192.168.2.16 \
  'sdk-deploy-rpm --silent --keepUserData /home/defaultuser/com.example.expenseslab2-1.0.0-4.armv7hl.rpm'
```

Телефон должен быть в режиме разработчика. В этой версии Авроры для обычного приложения используйте **sdk-deploy-rpm**: `devel-su rpm -Uvh` отвергает его как несистемный пакет. Если тихая установка запрещена настройками устройства, используйте `sdk-deploy-rpm --keepUserData ...` без `--silent` и подтвердите установку на телефоне.

Открыть значок **«Расходы ЛР2»**. Адрес сервера — `https://10.215.223.25:8443`, логин `demo`, пароль `demo12345`. Поле сертификата по умолчанию указывает на `/usr/share/com.example.expenseslab2/certificates/server.crt`. Нажать «Войти».

Новый расход — кнопка на экране или верхнее меню. Нажатие на запись открывает редактирование; долгое нажатие — контекстное меню удаления. Сумма вводится в рублях, например `125,50`, а передаётся как `12550` копеек.

## 6. Offline и синхронизация

1. Войти и дождаться загрузки расходов.
2. Включить «Работать offline»: приложение перестанет отправлять запросы.
3. Создать запись, изменить существующую, удалить другую. Изменения сохраняются в SQLite, отображается счётчик очереди.
4. Закрыть и снова открыть приложение: данные, токен, offline-переключатель и очередь сохраняются.
5. Выключить offline-переключатель: очередь отправится, затем загрузится серверный снимок.
6. Проверить результат в браузере. Для демонстрации реального отсутствия сети можно вместо переключателя отключить Wi-Fi на телефоне; приложение сохранит кэш и очередь после ошибки. После восстановления связи нажать «Синхронизировать» или дождаться фоновой попытки в активном приложении.

Очередь разделена по паре URL сервера + логин. Выход не удаляет неотправленные изменения. Автоматическая синхронизация не является системной фоновой службой: она работает, пока исполняется приложение.

Операция, которая уже отправлялась, имеет неизменные ключ и тело до получения ответа. Если исход отправки неизвестен из-за обрыва связи, её редактирование временно блокируется до повторной синхронизации. Это сохраняет корректность повторов; локальную запись приложение не теряет.

Конфликт: загрузить расход на телефон, перейти offline, изменить его. В браузере изменить тот же расход. После синхронизации появится блок с обеими версиями. «Принять серверную» отменяет локальную операцию; «Сохранить локальную» отправляет новую операцию поверх актуальной версии. Если запись удалена на сервере, сохранение локальной версии создаёт новый расход с новым UUID.

## Независимость клиентов

«Расходы ЛР2» (`com.example.expenseslab2`) и «Расходы · ЛР3» (`com.example.expenseslab3`) устанавливаются одновременно. Настройки, JWT, SQLite и offline-очередь разделены. Клиент ЛР2 использует HTTPS :8443; клиент ЛР3 — HTTPS/WSS :9443. Старое приложение `com.example.expenses` и его данные остаются на телефоне; автоматический перенос данных не выполняется.
