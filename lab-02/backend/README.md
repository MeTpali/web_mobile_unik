# FastAPI: сервер генератора для Flutter

## Назначение и структура

Вариант 6 второй лабораторной: сервер получает диапазон и возвращает случайное целое число. Основной обмен идёт через **WebSocket**, а не HTTP POST. Flutter-интерфейс здесь не создаётся.

- `app/main.py` — FastAPI, HTTP-диагностика, приём сообщений сокета и отключение клиента.
- `app/protocol.py` — JSON-протокол, идентификаторы запросов, формат ошибок.
- `app/generator.py` — строгая проверка границ и генерация через встроенный `secrets.randbelow`.
- `run.py` — запуск Uvicorn (ASGI-сервера), адрес и порт.
- `smoke_client.py` — консольная проверка настоящего WebSocket без мобильного приложения.
- `tests/test_backend.py` — автоматические проверки логики и WebSocket.
- `requirements.in` — перечень прямых зависимостей; `requirements.txt` — зафиксированные установленные версии всех зависимостей.

FastAPI описывает маршруты, Uvicorn принимает сетевые соединения, библиотека websockets обеспечивает транспорт. Генератор отделён от сети. await при получении сообщений позволяет обслуживать несколько клиентов; результат отправляется только тому клиенту, который его запросил. Общей истории и базы данных нет.

Официальный пример подхода: [WebSocket в FastAPI](https://fastapi.tiangolo.com/advanced/websockets/). Контракт именно нашего приложения описан ниже; Swagger `/docs` показывает HTTP-маршруты, но не позволяет тестировать этот WebSocket.

## Установка и запуск (PowerShell)

Проверяемое окружение: Python 3.13.2. Из корневой папки курса:

```powershell
cd lab-02/backend
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe run.py
```

Окружение и зависимости уже подготовлены в текущем workspace; для повторного запуска достаточно последней команды. Активация `Activate.ps1` не нужна, поэтому политика PowerShell не мешает запуску.

Параметры по умолчанию: **0.0.0.0:8000**. Остановка: Ctrl+C.

- Диагностика на ПК: `http://127.0.0.1:8000/health`, ответ `{"status":"ok"}`.
- WebSocket на ПК: `ws://127.0.0.1:8000/ws/random`.
- WebSocket с телефона: `ws://<IPv4-ПК>:8000/ws/random`.

Для другого порта задайте `$env:PORT = '8001'` перед запуском. При необходимости адрес задаётся через `$env:HOST`. Не используйте `0.0.0.0` или `localhost` в настройках клиента на телефоне: укажите реальный адрес ПК из `ipconfig`. ПК и телефон должны видеть друг друга в локальной сети; брандмауэр должен разрешать входящие подключения на выбранный порт. Проверка на физическом телефоне пока не выполнена.

## Контракт для будущего Flutter-клиента

1. Установить одно соединение с `/ws/random`.
2. Дождаться успешного подключения.
3. Отправлять **текстовые** WebSocket-сообщения с JSON-объектом.
4. Читать JSON-ответы из потока этого же соединения.
5. По `type` различать `result` и `error`, по `request_id` — сопоставлять ответы.
6. При выходе закрывать соединение; после сетевого разрыва подключаться заново.

Сервер не отправляет приветствие. На одно прикладное сообщение приходит один ответ. В рамках одного соединения сообщения обрабатываются последовательно. Нет рассылок всем клиентам и автоматической повторной генерации. Переподключение не восстанавливает старые запросы: при необходимости клиент отправляет их снова. `request_id` — только корреляция, не гарантия идемпотентности: повтор того же ID вызывает новую генерацию.

### Запрос

```json
{"type":"generate","request_id":"request-1","min":1,"max":100}
```

| Поле | Правило |
| --- | --- |
| `type` | Обязательная строка `generate` |
| `request_id` | Необязательная строка 1–64 символа; допускается null; при отсутствии ответ содержит null |
| `min` | Обязательное целое JSON-число от −1 000 000 000 до 1 000 000 000 |
| `max` | Такое же число, не меньше min |

Неизвестные поля отклоняются. Строки `"1"`, boolean, null и дробные значения границ не принимаются. Числа передавайте в JSON как целые: запись `1.0` также отклоняется строгой проверкой. Обе границы включены. Отрицательные диапазоны допустимы; при min=max возвращается это число. Повторы результатов нормальны.

### Успех

```json
{"type":"result","request_id":"request-1","min":1,"max":100,"value":42}
```

42 — пример, фактическое число случайно. `min` и `max` позволяют подписать результат исходным диапазоном.

### Ошибка

```json
{"type":"error","request_id":"request-1","error":{"code":"INVALID_RANGE","message":"Минимум не должен превышать максимум"}}
```

| Код | Причина | Соединение |
| --- | --- | --- |
| `INVALID_JSON` | Повреждённый JSON, NaN или Infinity | Остаётся открытым |
| `INVALID_REQUEST` | Не объект, неверный ID или лишние поля | Остаётся открытым |
| `UNKNOWN_TYPE` | Нет type либо неизвестная операция | Остаётся открытым |
| `INVALID_RANGE` | Отсутствующие/неверные границы | Остаётся открытым |
| `UNSUPPORTED_FRAME` | Бинарное сообщение вместо текстового | Остаётся открытым |
| `MESSAGE_TOO_LARGE` | Текстовое сообщение больше 4096 байт UTF-8 | Остаётся открытым |
| `INTERNAL_ERROR` | Непредвиденный сбой | Сервер закрывает с кодом 1011 |

Если JSON нельзя разобрать или ID некорректен, ответ содержит `request_id: null`. При корректном ID и неверном диапазоне ID возвращается без изменения.

Ошибки после подключения передаются внутри JSON, а не HTTP-статусами 400/500. Uvicorn дополнительно ограничивает целое входящее WebSocket-сообщение 64 КБ: при превышении транспортного лимита соединение закрывается (1009) без прикладного JSON. Закрытие сети тоже не гарантирует JSON-ответ: Flutter должен отдельно обрабатывать завершение/ошибку потока. Ping/pong транспорт обслуживает автоматически; прикладной операции `ping` нет.

## Проверка без Flutter

При работающем сервере во втором терминале из `backend`:

```powershell
.\.venv\Scripts\python.exe smoke_client.py
```

Проверяются обычный диапазон, равные отрицательные границы, ошибочный диапазон и успешный запрос после ошибки на том же соединении. Для другой машины/порта:

```powershell
.\.venv\Scripts\python.exe smoke_client.py --url ws://192.168.1.10:8000/ws/random
```

Автоматические проверки не требуют отдельно запущенного сервера:

```powershell
.\.venv\Scripts\python.exe -m pytest -q
.\.venv\Scripts\python.exe -m pip check
```

Тесты проверяют граничные диапазоны, строгие типы, повреждённые сообщения, ограничение размера, бинарные кадры, сохранение соединения после ошибок, независимость двух клиентов и переподключение. Проверки случайных результатов не требуют уникальности и не доказывают статистическое распределение.

## Результаты серверных проверок

- Python 3.13.2; версии пакетов зафиксированы в `requirements.txt`.
- 27 автоматических тестов прошли без предупреждений.
- `pip check`: несовместимых зависимостей нет.
- Uvicorn запущен на 0.0.0.0:8000; консольный клиент успешно выполнил четыре обмена по настоящему WebSocket, включая восстановление после ошибки.
- Подключение физического телефона и работа Flutter/Авроры не проверялись.

## Что останется сделать в мобильном приложении

Форма диапазона, кнопка, состояния подключения/ожидания/ошибки/результата, сериализация запроса и разбор ответов по этому контракту. Указывайте IP ПК и обрабатывайте потерю связи. Мобильный клиент и демонстрация на ОС Аврора нужны для полной лабораторной, но не входят в выполненную серверную часть.
