# Снимки для отчёта по ЛР3 · вариант 1

Нужно **3 изображения**: push на телефоне, работа после отказа backend, результат blue-green. Сборку RPM и проверку балансировки отдельно фотографировать не нужно. Номера совпадают с разделом 2.5 отчётов MD/DOCX в `../reports/Отчёт_ЛР_03`.

## Перед началом

1. Серверная инфраструктура уже должна быть установлена; обе группы blue/green должны иметь подготовленные релизы. Если стенд ещё не развёрнут, сначала выполните первоначальную установку из `README.md`. Сборку RPM повторять для этих кадров не требуется — приложение уже установлено.
2. Используем адрес ноутбука **192.168.0.104**, HTTPS-порт **9543**. Телефон должен иметь сетевой маршрут к этому адресу. SSH `192.168.2.16` нужен для управления телефоном, это не URL API. Если IP изменился, сначала обновите URL и сертификаты.
3. Новые сертификаты встроены в приложения. Если ещё не применяли соответствующий сертификат к nginx, выполните один раз:

```bash
cd ~/Unik/web_mobile_unik/kirik/lab3
sudo bash deploy/scripts/update-tls.sh
```

4. Откройте два терминала ноутбука — A для состояния и ручного отказа, B для автоматического сценария. Все команды выполняются **на ноутбуке**, кроме указанных нажатий на телефоне. Запрос `sudo` требует пароль пользователя ноутбука; в инструкции его нет.
5. В терминале A подготовьте исходное состояние blue и проверьте HTTPS. Эти команды — подготовка, отдельный снимок не нужен:

```bash
cd ~/Unik/web_mobile_unik/kirik/lab3
export LAB_URL=https://192.168.0.104:9543
sudo systemctl start postgresql nginx
sudo bash deploy/scripts/switch-release.sh blue
curl --fail --cacert certificates/server.crt "$LAB_URL/ready"
```

Дождитесь успешного ответа готовности; при ошибке TLS примените сертификат командой из пункта 3. Backend ЛР3 запускаются через systemd, `backend/run.py` для этого стенда запускать не нужно.

6. На ноутбуке снимайте окно терминала штатным инструментом ОС; экран телефона фотографируйте другим устройством. Создайте каталог для готовых изображений:

```bash
cd ~/Unik/web_mobile_unik/kirik/lab3
mkdir -p docs/screenshots/manual
```

Сохраняйте PNG или JPG с именами ниже. По одному кадру на рисунок, без дополнительных фото настроек. Пароли и JWT в кадр не включайте.

## Последовательность кадров

### 3.1. Получение push-уведомления в мобильном приложении

Файл: `lr3-01-push.png` (или `.jpg`).

1. На телефоне откройте **«Задачи ЛР3»**. Нажмите «Настройки» внизу экрана. На открывшейся странице найдите блок «01 / Подключение»: в «Адрес сервера» введите `https://192.168.0.104:9543`, в «Доверенный сертификат» — `/usr/share/ru.kirik.taskslab3/certificates/server.crt`. В блоке «03 / Синхронизация» выключите «Работать offline». В блоке «02 / Учётная запись» введите `demo` и `demo12345`, нажмите «Войти». После успешного входа вернитесь назад жестом от левого края вправо.
2. На главном экране найдите карточку подключения: блок «Уведомления · WSS» должен показывать имя backend (`blue-1` или `blue-2`) и «Активное соединение». Блок HTTP/REST показывает backend последнего HTTP-ответа; он может отличаться от WSS. Не переходите к отправке уведомления, пока WSS не подключился.
3. На ноутбуке откройте в браузере **https://192.168.0.104:9543/** — главную страницу, без `/docs`. При запросе доверия подтвердите именно учебный сертификат. В форме входа введите `demo` / `demo12345` и нажмите «Войти». Телефон и браузер должны работать под одним пользователем.
4. На странице найдите форму записи. При необходимости нажмите «Очистить форму», чтобы создать новую запись, а не изменить старую. Заполните: «Срок» — будущая дата, «Заголовок» — `Фото push`, «Статус» — «К выполнению», «Описание» — `Проверка уведомления`.
5. Подготовьте камеру другого устройства, направив её на экран телефона. Оставьте приложение открытым, online, экран разблокированным. На ноутбуке нажмите **«Сохранить»**.
6. На телефоне не нажимайте обновление. Дождитесь автоматического появления записи и баннера уведомления. Сделайте **одно фото баннера на фоне приложения**. Если баннер исчез, откройте штатный экран уведомлений/шторку и снимите запись там — второй кадр вместо первого не нужен. Это рисунок 3.1.
7. Если уведомления нет, проверьте подключение WSS и совпадение пользователя. В браузере у созданной записи нажмите «Изменить», измените описание/комментарий и нажмите «Сохранить», чтобы получить новое событие. Полностью закрывать процесс приложения нельзя: push работает через его активное WSS-соединение.

### 3.2. Работа мобильного клиента после отказа backend

Файл: `lr3-02-failover.png` (или `.jpg`).

1. Оставьте приложение online. На главном экране найдите карточку подключения: блок «Уведомления · WSS» должен показывать имя backend (`blue-1` или `blue-2`) и «Активное соединение». Блок HTTP/REST показывает backend последнего HTTP-ответа; он может отличаться от WSS. Запишите текущее имя WSS backend. Например, если это `blue-1`, останавливайте `blue-1`; если `blue-2` — только `blue-2`.
2. В терминале A выполните блок ниже. В строке `FAILED=blue-1` укажите имя, которое только что увидели на телефоне:

```bash
cd ~/Unik/web_mobile_unik/kirik/lab3
FAILED=blue-1
sudo systemctl stop "kirik-tasks@$FAILED"
systemctl is-active kirik-tasks@blue-1 kirik-tasks@blue-2
```

Ожидается один `inactive` и один `active`. Ненулевой код `is-active` при остановленном экземпляре здесь ожидаем.
3. Не нажимайте на телефоне «Войти», «Обновить» или «Синхронизировать»: дождитесь автоматической повторной попытки. Статус WSS должен показать второй backend. Если видите старое имя, ещё подождите; при длительной ошибке проверьте, что второй сервис остался активен.
4. В браузере ноутбука на странице из шага 3.1 нажмите «Очистить форму». Заполните те же поля, но замените заголовок/комментарий `Фото push` на **`Фото после отказа`**. Нажмите «Сохранить».
5. Дождитесь автоматического появления новой записи на телефоне. Сделайте **одно фото приложения с подключённым WSS ко второму backend**; по возможности оставьте в кадре и новую запись. Это рисунок 3.2. Важно дождаться нового ответа/события: старый кэшированный список сам по себе не подтверждает работу после отказа.
6. После снимка восстановите остановленный экземпляр в том же терминале:

```bash
sudo systemctl start "kirik-tasks@$FAILED"
systemctl is-active kirik-tasks@blue-1 kirik-tasks@blue-2
```

Оба сервиса должны вернуть `active`. Не останавливайте оба экземпляра одновременно.

### 3.3. Обновление версии blue-green без ошибок запросов

Файл: `lr3-03-blue-green.png` (или `.jpg`).

1. Убедитесь, что оба blue backend восстановлены после предыдущего шага. Телефон оставьте в приложении online, браузер можно оставить открытым. На этом шаге не нужно вручную нажимать переключение версии или обновление на телефоне.
2. В терминале B на ноутбуке выполните:

```bash
cd ~/Unik/web_mobile_unik/kirik/lab3
set -o pipefail
sudo /opt/kirik-tasks/venv/bin/python deploy/scripts/exercise-cluster.py | tee /tmp/kirik-tasks-lab3-demo.log
```

Скрипт сам выполняет непрерывные HTTPS-запросы, отказ backend, переключение blue → green и возврат на blue. Дождитесь окончания и настоящей строки `PASS: failover, push reconnect, blue-green, rollback, no HTTP downtime`. Пока сценарий работает, посмотрите на телефон: после разрыва WSS он должен переподключаться. Текущие версии backend смотрите в результатах; они не равны версии RPM клиента.
3. Если скрипт завершился ошибкой или вместо PASS вывел исключение, снимок успешного обновления пока не делайте: устраните проблему и повторите команду. Старый JSON предыдущего запуска не используйте как новый результат.
4. После успешного завершения выведите компактную сводку и последнюю строку текущего журнала:

```bash
clear
python3 -c 'import json; d=json.load(open("docs/cluster-validation.json")); print(json.dumps({k:d[k] for k in ("requests", "backends", "failures")}, ensure_ascii=False, indent=2))'
tail -n 1 /tmp/kirik-tasks-lab3-demo.log
```

5. Проверьте: `requests` больше нуля, в `backends` есть blue и green с разными версиями, `failures` — пустой список `[]`, последняя строка — реальный PASS. Сделайте **один снимок терминала** с этой сводкой. Это рисунок 3.3; длинный журнал целиком не нужен.
6. Скрипт возвращает маршрутизацию на blue. Можно проверить итог без дополнительного фото:

```bash
curl --fail --cacert certificates/server.crt https://192.168.0.104:9543/meta
```

Этот тест подтверждает отсутствие ошибок у выполнявшихся тестовых запросов во время обновления; состояние телефона проверяется отдельно наблюдением за приложением.

## Вставка и завершение

В DOCX замените строку `[Место для изображения: …]` фотографией через «Вставка → Изображения», подпись оставьте под ней. В MD замените строку ссылкой вида `![Описание](../lab3/docs/screenshots/manual/lr3-01-push.png)`. Не запускайте генератор отчётов после ручной вставки без резервной копии: он перезаписывает отчёт.

Убедитесь, что три файла читаемы и соответствуют рисункам 3.1–3.3. Удалите через интерфейс только свои записи «Фото push» и «Фото после отказа». Для очистки используйте «Удалить» в браузере и подтвердите действие. Дождитесь обновления телефона. Кластер после сценария оставьте на blue. Отдельные кадры RPM и балансировки исключены; оставшиеся рисунки перенумерованы с 3.1 по 3.3.
